## 用户需求

用户要求直接启动迭代 A 的 S1（双身份登录体系）并同步 S2（药师审核工作台），且授权运行命令全部允许、无需逐个确认。

## 产品概述

当前小程序仅有"患者一键登录 + 医师工作台跳转"的雏形，微信登录 `login_wx` 把 role 硬编码为 patient，后端 `dev_token` 白名单缺 doctor/pharmacist，药师审核接口权限挂在 doctor/platform 上却无药师实体与工作页面。本任务打通"患者/医师/药师"三类身份的真实登录与鉴权，并补齐药师审核工作台，使"开方 -> 药师审核 -> 凭方购药"业务闭环成形。

## 核心特性

- S1 双身份登录体系：后端支持 patient/doctor/pharmacist 三类身份签发 JWT；新增 `IhPharmacist` 实体；`login_wx` 按身份参数关联对应档案并签发正确 role；`dev_token` 补白名单；小程序登录页身份选择 + 登录后按 role 路由工作台。
- S2 药师审核工作台：处方审核接口权限修正为药师/平台；前端新增药师审核页（列表待审、详情、通过/驳回）；`audit_prescription` 的 reviewer_id 取当前 JWT 主体（更安全）；药师登录后进入审核工作台。
- 以 openapi.json 为契约事实源，前端 service 与后端端点字段严格对齐；run 命令授权执行。

## 技术栈选型

- 后端：Python FastAPI + SQLAlchemy 2.x（异步）+ Alembic 迁移（沿用现有栈，不引入新依赖）
- 前端小程序：Taro(React) + TypeScript（沿用现有栈）
- 鉴权：JWT（HS256）+ RBAC；统一响应体 `code/message/data`（HTTP 200 + 业务码）
- 验证：dev-token 端点 + curl 真联调

## 实现方法

采用"先后端数据模型与鉴权，再接口权限修正，后前端页面与路由"的顺序，避免契约漂移。

### 关键技术决策

1. **新增 `IhPharmacist` 实体（含迁移）**：与 `IhDoctor` 同构（`user_id` FK、`license_no`、`status`），药师身份持久化，使 role=pharmacist 的 JWT 能关联到真实档案，符合等保三级"身份可追溯"要求。迁移新建 `0012_ih_pharmacist.py`，幂等建表。
2. **`login_wx` 支持身份参数**：`UserLoginWxIn` 增加可选 `role`（默认 patient）与 `doctor_id`/`pharmacist_id` 关联线索（开发态可直接传）。登录时按 role 取对应档案 id 写入 JWT subject（patient 用 user.id；doctor/pharmacist 用档案.id），返回 `user.role` 透传前端路由。保持"未配 appid 走 dev_{code}"的本地联调兼容。
3. **`dev_token` 白名单补 doctor/pharmacist**：`MT_ROLES` 扩为六角色全集，使前端联调可签发医生/药师令牌；修复"选 doctor 登录 400"的现存 bug。
4. **审核权限语义修正**：`audit_prescription` 由 `require_role("doctor","platform")` 改为 `require_role("pharmacist","platform")`；`reviewer_id` 改为取 `actor_of(_user)`（当前 JWT 主体）而非前端传入，杜绝伪造审核人，审计链更可信（与 R5 既有约定一致）。
5. **前端身份路由**：登录页三态选择（患者/医师/药师），登录后按 `user.role` 存 Storage 并 `reLaunch` 到对应工作台（患者→index、医师→doctor-workbench、药师→pharmacist-review）；services `TokenData.user` 增加 `role`，`Prescription` 增加 `pharmacist_id`。
6. **新增药师审核页 `pages/pharmacist-review`**：列表 `listPrescriptions({status:'pending_audit'})`、点击进详情、通过/驳回调用新增 `auditPrescription`。复用 `prescription-detail` 的卡片样式，保证 UI 一致。

### 性能与可靠性

- 迁移与 seed 幂等；`login_wx` 不做额外查库（沿用现有模式，不查库校验 user 存在）；审核接口仅需一次 `db.get` + `db.commit`，O(1)。
- 不引入新依赖、不改响应体结构，沿用统一 `success/error` 包装。
- uvicorn `--reload` 对 schema/route 改动在本地可能需手动重启；计划中标注重启验证。

## 实现注意（防回归）

- **勿整文件覆盖**：改 service/页面前必 read 确认已存在内容（此前曾误覆盖致 TS2305）。
- **角色单一来源**：所有 role 常量以 `deps.ROLES` 为准，新增 pharmacist 同步到 `ROLES`、`MT_ROLES`、`dev_token` 白名单、前端登录选项，避免散落硬编码。
- **审计链正确**：审核 `reviewer_id` 取 `actor_of(_user)`（JWT sub），不依赖前端传值，防止越权伪签。
- **敏感信息**：`.env` 不入库；日志不打印 JWT_SECRET。
- **范围控制**：仅做 S1/S2，不铺 P2 微信支付真调起、不做账号密码体系改造；药师档案创建走开发态/种子，不实现药师注册流（属后续迭代）。
- **向后兼容**：`login_wx` 的 `role` 参数默认 patient，旧调用不受影响；`UserOut` 增加 `role` 字段需确认不影响 admin-web（admin-web 用 `/auth/login`，独立 schema）。

## 架构设计

沿用现有分层（路由层 / 依赖注入 / 模型 / schema / 服务），仅新增实体与页面，不引入新架构。后端鉴权流：

```mermaid
flowchart TD
  A[小程序登录页 选身份] --> B[POST /ih/users/login/wx role=...]
  B --> C{role}
  C -- patient --> D[签发 role=patient JWT sub=user.id]
  C -- doctor --> E[关联 IhDoctor 签发 role=doctor sub=doctor.id]
  C -- pharmacist --> F[关联 IhPharmacist 签发 role=pharmacist sub=pharmacist.id]
  D/E/F --> G[前端按 role 路由工作台]
  H[药师工作台] --> I[GET /ih/prescriptions?status=pending_audit]
  I --> J[PATCH /ih/prescriptions/{id}/audit action=reviewer_id=JWT sub]
  J --> K[rx.pharmacist_id=actor_of / status=approved]
```

## 关键验证清单（curl/dev-token 实测）

1. `POST /auth/dev-token {"role":"pharmacist","sub":"1"}` → 200 且返回 token（白名单修复）
2. `POST /ih/users/login/wx {"code":"x","role":"pharmacist"}` → 200 且 data.user.role=pharmacist
3. `POST /ih/users/login/wx {"code":"x"}` → 默认 role=patient（向后兼容）
4. `GET /ih/prescriptions?status=pending_audit` 用 pharmacist token → 200 列表
5. `PATCH /ih/prescriptions/{id}/audit {"action":"approve","note":""}`（pharmacist token）→ 200，库 pharmacist_id=当前 sub
6. `PATCH /ih/prescriptions/{id}/audit` 用 doctor token → 403（权限收紧验证）
7. 前端 tsc 通过；药师页可列待审、可审核

- Expected outcome: 每次修改或比对都返回准确的现有代码结构与端点定义，保障改动精准、零回归
